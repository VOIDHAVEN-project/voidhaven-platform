## 1. 目的与边界

本规范定义项目从“本地可运行”走向“可控测试和正式运行”时的最小运行纪律：环境、访问、密钥、数据、媒体、日志、监控、备份、恢复、发布、回滚和事故处理怎样互相配合。

它的目标不是在项目还未选择供应商时假装已经有生产系统，而是先让未来每一次外部操作都可回答：在哪个环境、由谁批准、影响什么数据、如何观察、失败后如何恢复、备份何时过期、何时需要通知项目负责人。

本规范不选择具体云厂商、部署平台、数据库实例、对象存储桶、邮件/短信服务、域名、CDN、监控产品、团队联系人或生产密钥；它也不授权创建任何此类资源。选型和实际操作必须有单独 M0/DR 与项目负责人明确确认。

### 2.2 总原则

1. **环境分离。** 本地、测试和生产使用独立配置、独立权限和独立数据边界；生产数据不因调试方便流入本地或测试。
2. **最小权限。** 人和服务使用可追溯的最小账户权限；不共用匿名管理员、不把生产密钥发进聊天、代码、截图或日志。
3. **可恢复优于可部署。** 每次影响真实数据的发布都先说明备份、迁移和回滚路径；未验证恢复的备份不能算可靠备份。
4. **可观察但不收集过度。** 运行日志和监控只收集排障、审计和安全所需的最小事实，继承 S-04 的隐私/留存要求。
5. **发布是受控变化。** `main` 不等于生产；测试通过不等于可以发布；任何生产发布、回滚、迁移或密钥变更都需要项目负责人明确确认。
6. **安全默认拒绝。** 密钥、私密联系人、群二维码、完整请求体、富文本危险输入、媒体二进制、内部审核材料和原始网络标识都不进入公开路径、常规日志或无边界备份。

## 3. 环境与配置基线

### 3.1 三类环境

| 环境 | 用途 | 数据与访问边界 | 发布/变更规则 |
| --- | --- | --- | --- |
| local | 开发、学习复现、组件/Mock/本地服务验证 | 只使用 Mock、合成数据或经批准的最小脱敏测试数据；不得包含生产密钥或生产私密信息。 | 每个已批准模块可在候选代码分支中使用；本地运行不等于部署。 |
| test | 集成、回归、手工验收、受控演练 | 与生产隔离；默认使用合成数据。若因验收需要使用真实数据，先走单独 DR/确认并采用最小、脱敏、可清理副本。 | 创建/修改环境、测试数据库、测试域名或外部服务均需项目负责人明确授权。 |
| production | 面向真实公开访客与受限合作方/管理员的正式服务 | 只保存 S-04/S-06 允许的数据；访问采用最小权限、审计和保留/删除机制。 | 只从已验收版本发布；每次发布、回滚、真实迁移、密钥/权限变更均需明确批准。 |

测试环境可以在未来被称为 staging，但它是环境而不是长期 Git 分支。代码仍按 S-02 使用 `main`、`feature/*`、`fix/*`、`bootstrap/*`、`release/*` 和 `hotfix/*`。

### 3.2 配置与环境变量

- 每个变量在创建前登记：名称、用途、所属环境、是否敏感、拥有者、最后验证时间和轮换/失效方式；登记位置不得包含变量真实值。
- 真实值只进入受控的环境变量/密钥系统或本地未提交文件；仓库只可保存 `.env.example` 中的变量名、说明和安全示例。
- 浏览器构建可见的变量只能包含本来就可公开的值；不得把数据库密码、私钥、管理 token、社群入口、内部 API 密钥或后台控制值暴露给前端。
- 不以 `console.log`、异常上报、截图、文档、Issue、测试 fixture 或 Git commit 传递密钥；发现疑似泄露时立即停止传播、撤销/轮换并记录影响。
- 同一环境的配置变更要有变更人、目的、时间、影响服务与验证/回退说明；不通过修改源码硬编码环境差异。

## 4. 数据、媒体、备份与恢复

### 4.1 数据与媒体运行边界

- 云端 MySQL 未来保存业务数据、富文本元数据和媒体引用；图片二进制不进入 MySQL 正文或公开 JSON。
- 认证后的受限图片上传、对象存储、病毒扫描、CDN、媒体删除和过期清理由后续模块在 S-06 边界内落地；不能因为存储方便而允许匿名文件上传。
- 备份、导出、日志和恢复副本也属于数据处理。它们必须遵循 S-04 的最短必要留存、私密字段最小化、删除/去标识化和访问审计要求。
- 任何本地/测试数据导入、生产数据导出、人工修复、批量更新或恢复操作都要先说明对象范围、数据类别、权限、备份、验证和回退方式。

### 4.2 备份最小要求

1. 启用真实 MySQL 或媒体存储前，必须确定自动备份频率、保留期、加密方式、访问角色、存放位置、失败告警和恢复责任人。
2. 备份至少覆盖恢复公开/受限业务所必需的数据和媒体引用；如媒体与数据库分离，必须说明二者如何按一致时间点恢复或验证。
3. 备份不得被公开访问，也不得用普通应用账号读取；备份访问、导出、下载、恢复和删除应产生最小审计证据。
4. 删除/去标识化的私密数据不得因备份而无限期留存。每类备份必须有可验证的过期/清理边界，并与 S-04 第 7.3 节的处理目的和留存基线协调。
5. 每次真实恢复演练应记录：数据时间点、恢复对象、操作人、耗时、完整性检查、是否影响外部用户、后续清理和发现的问题；演练使用隔离环境，除非项目负责人另行批准。

### 4.3 数据库迁移与回退

- 每个真实 schema 变更都必须来自已批准模块，具有可检索迁移 ID、目的、前置版本、受影响数据、向前/向后兼容性、验证和回退/修复计划。
- 先执行可逆或兼容性迁移，再发布依赖它的应用版本；不得把不可逆删除、表重建、大范围数据修正混入普通功能发布。
- 迁移前确认最近可用备份和恢复路径；迁移后执行最小数据完整性和权限检查。失败时优先停止进一步写入、评估回滚/修复，不能无证据重试。
- 不在本地或测试中使用真实生产凭据执行迁移；不在没有明确确认时创建真实数据库、清空表、删除备份或回滚数据。

## 5. 日志、监控、审计与隐私

### 5.1 可记录与不可记录

| 类别 | 可以记录的最小信息 | 禁止进入常规日志/监控 |
| --- | --- | --- |
| 运行错误 | 时间、服务/路由、稳定错误码、请求关联号、可重试性、已脱敏的上下文 | 密钥、完整请求/响应、SQL、堆栈中的私密值、媒体二进制。 |
| 业务安全事件 | 操作类型、对象类型/不透明 ID、角色、成功/失败、时间、必要原因摘要 | 私人联系方式、完整匿名答案、群二维码、未审核正文、原始网络标识。 |
| 发布/迁移/恢复 | 版本、环境、操作人、时间、结果、回退关联号 | 生产凭据、备份下载地址、数据库连接串、完整敏感数据。 |
| 性能/可用性 | 延迟区间、错误率、资源/队列健康、备份任务成功与否 | 用于追踪个人的长期标识或超出目的的行为画像。 |

- 日志需使用可检索的结构化字段和关联号；面向用户的错误显示与运维日志分离。
- S-04 已确定：非敏感异常摘要默认 14 天、匿名限流事件 7 天、关键管理员审计 180 天等基线。S-08 在真实上线前必须按实际工具和法律适用性复核，而非自动延长。
- 监控、错误上报、分析和告警服务属于第三方数据处理；启用前要说明发送字段、区域、保留期、访问角色、费用和关闭/删除方式。
- 公开状态与受控响应缓存必须遵循 S-06：会话、私密联系方式、受控社群入口和审核数据使用 `Cache-Control: no-store` 或等价隔离；隐藏内容不能继续由旧缓存公开。

### 5.2 最小可观察性

正式运行前至少应能发现并追溯：服务不可用/高错误率、关键公开读取失败、受控会话/权限异常、投稿或审核写入失败、备份失败、迁移失败、异常上传拒绝、管理员关键动作与密钥/权限变更。

告警不应直接发送敏感正文或凭据。告警接收人、升级方式和值守安排是运维责任配置，须在选定运行环境时单独确认。

## 6. 发布、回滚与事故处理

### 6.1 受控发布流程

1. **候选完成：** 模块满足 S-07 和 M3 验收，已说明相对 `main` 的差异、测试、人工验收、数据/隐私影响和已知限制；
2. **测试验证：** 在获授权的 test 环境执行部署/迁移/Smoke Test，使用合成或获批的最小数据；
3. **发布批准：** 项目负责人明确确认版本、环境、时间窗口、数据迁移、回滚路径、责任人和通知范围；
4. **生产发布：** 记录版本/提交、配置版本、迁移 ID、开始/结束时间、操作人、Smoke Test 与观察窗口；
5. **发布后观察：** 核查核心公开路径、受限路径、错误率、备份/任务、日志异常和敏感信息泄露风险；
6. **收口：** 更新发布记录、已知问题、回滚准备和后续任务。没有单独确认，不从 `main` 自动发布。

### 6.2 回滚与紧急下线

- 应用回滚使用先前已验证版本；配置回滚不得恢复已经轮换/撤销的密钥；数据迁移回滚只在事先证明可安全执行时进行。
- 内容或隐私风险优先使用 S-04 的 `HIDDEN`、受控入口关闭、权限撤销或服务降级；不得为“恢复速度”而物理删除审计证据。
- 数据损坏、错误公开或安全事件先限制写入/公开范围，保存最小证据，再依据已批准路径恢复或修复；恢复后必须进行完整性和隐私复核。
- P0（疑似敏感泄露、非法权限、不可控数据损坏）立即停止受影响公开/写入路径并通知项目负责人；P1（核心公开或受限能力不可用）优先恢复服务或回滚；P2（局部降级）记录、评估和计划修复。具体联系人、响应时间和对外沟通模板不在本规范中假定。

### 6.3 运行手册

每个真实运行服务在上线前至少有一份受控运行手册，包含：服务/环境用途、拥有者、依赖、健康检查、常见告警、部署/回滚入口、备份/恢复步骤、迁移步骤、密钥轮换、日志位置、数据删除边界和何时升级给项目负责人。手册不得包含真实密钥、私人联系方式或公共可见的受控入口。

## 7. 安全基线

- 生产和受限管理访问使用个人可追溯账户、最小角色和尽可能的多因素保护；共享管理员凭据、长期默认密码和在前端保存长期 token 均不允许。
- 访问权限的创建、扩大、撤销、密码/激活材料重置和高风险操作须有审批与审计；人员/合作关系变化后及时复核。
- 浏览器、API、数据库、对象存储、备份、日志与 CI（如未来启用）按独立凭据和最小网络边界配置；一个前端公开密钥不得同时拥有后台或数据库权限。
- 依赖漏洞、构建工具升级和安全修复应记录影响版本、验证和回退；紧急修复走 S-02 的 `hotfix/*` 规则，不绕过发布确认。
- 任何疑似密钥、隐私数据、权限或供应链风险均是停止信号：暂停相关发布/传播，保留最小必要证据，轮换/撤销并通知项目负责人。

## 9. 批准状态与维护条件

本规范已于 2026-08-30 通过第 4 批整体批准。以下条件是该次批准时已满足的基线要求，也是后续维护时必须继续保持的约束：

1. 第 8 节 S08-O1 至 S08-O5 已按项目负责人确认的推荐方案正确回填；
2. S-04 的留存/删除表、S-06 的隐私/缓存/API 规则和 S-07 的质量门均能在运行流程中得到贯彻；
3. 不存在把具体云厂商、账号、密钥、域名、告警联系人、成本或真实数据当作已获授权事实的内容；
4. 本规范现在可作为任何环境、数据库、部署、备份或发布模块 M0 开工卡的运行基线；每一次真实外部操作仍须遵循 S-02 的模块开工、验证与明确批准流程。
