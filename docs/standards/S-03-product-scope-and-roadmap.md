## 1. 目的与适用边界

本规范将“长期想成为怎样的平台”和“哪一阶段必须做什么”分开，避免把开发期的最小验证误解为正式产品的永久删减，也避免把长期愿景一次性塞进实现。

本规范只定义产品范围、用户、核心路径、版本门槛和明确不做项。字段、权限、审核、状态机和隐私由 S-04 定义；具体页面、导航视觉和路由由 S-05 定义；接口和实现细节不在本文件裁决。

## 2. 产品定位

VOIDHAVEN 的长期定位是：面向校内学术成长与可信协作机会的发现、审核、资源沉淀和社群导流平台。它以网站承载公开信息与可持续知识资产，以校内社群承载后续沟通和实际协作。

竞赛信息与可信招募是重要入口，但不是产品的全部。学习资源、经验文章、项目/代码资源与后续的学术社群内容，同样是平台持续存在的理由。

### 2.1 首次正式服务范围

| 项目 | 当前草案结论 |
| --- | --- |
| 首批重点人群 | 本校学生，先以信息工程及相邻工科学生为重点，再根据运营能力扩展。 |
| 校内组织 | 学术类学生组织、竞赛团队、指导老师及有可信资源/经验的合作方可成为服务和合作对象。 |
| 校外公开内容 | 平台自有或经审核公开的资源、经验、项目等可向所有公开访客阅读。原创或已获授权内容能否转载、下载、改编或二次使用，以每条内容的明确复用声明为准；外部第三方资源默认只展示摘要、来源和原链接，不代表平台转授复用许可。 |
| 公开投稿 | 内容投稿/反馈入口向所有公开访客开放，无需普通账号；投稿先进入审核，不能自动公开，也不因此开放校内社群、合作方后台或普通学生账号。 |
| 校外竞赛/招募/内部社群 | 首次正式上线不以对外开放为目标；如需开放，必须单独通过 DR 裁决。 |
| 学生社群 | QQ/微信等社群面向校内目标人群，入口不可无门槛公开。 |

### 2.2 语言与外语资源

简体中文是平台界面、表单、审核和结构化说明的正式语言。公开内容可使用中文、英文、中英双语或其他语言，但每条公开内容均需显示语言标签；非中文内容必须保留原始标题和来源，并提供中文导读、摘要或说明，帮助中文校园用户判断内容是否适合自己。中文说明不等于全文翻译，译文或改编内容仍须遵守 DR-003 的来源、权利来源和复用声明规则。

R1/R2 不承诺界面语言切换、自动翻译、跨语言搜索或完整国际化；这些能力需要依据未来使用证据另建 DR。具体语言字段和页面呈现规则见 DR-004，并分别由 S-06、S-05 细化。

## 3. 用户类型与价值

| 用户 | 获得的价值 | 不应承担的行为 |
| --- | --- | --- |
| 公开访客 | 阅读已公开的资源、经验、项目和必要公开信息；可免注册提交内容线索、资源、经验、项目或反馈 | 不因浏览或投稿被要求建立普通账号、提交简历或公开私人联系方式；投稿不自动公开。 |
| 本校学习者 | 发现竞赛、学习资源与可信招募；通过受控入口进入校内社群；可提交内容线索或作品 | 不在站内聊天、投递简历、接受面试或建立普通账号。 |
| 可信合作方 | 申请成为合作方后，管理自己名下的竞赛/招募/资源候选内容 | 不可查看其他合作方或学生的私人信息，也不可绕过审核直接公开。 |
| 管理员 | 核验、审核、发布、更新、下线与归档内容；维护对外信息质量 | 不应把社群内报名、聊天、面试等外部过程搬回站内保存。 |

## 4. 产品责任边界

| 网站负责 | 社群或外部渠道负责 |
| --- | --- |
| 公开内容展示、审核、来源说明、更新、可见性、归档和资源沉淀 | 进群后的自我介绍、沟通、组队、报名、简历、筛选、面试和持续关系维护 |
| 将符合条件的用户导向受控 QQ/微信入口或经审核的外部页面 | 具体报名表、面试安排、群内规则和即时消息 |
| 为合作方提供受限内容管理能力 | 线下/群内的人员匹配和团队内部管理 |

网站展示的竞赛说明、截止时间和资源解释不能替代官方规则。涉及正式报名、资格或规则变化时，用户应以对应官方来源或组织方通知为准。

## 5. 首次正式产品的核心路径

### P-01：竞赛发现

学习者浏览和筛选竞赛，查看可核验的基本信息、截止时间和官方来源；如存在适合的可信招募或校内社群入口，可按规则继续进入外部流程。平台不保存其报名或简历。

### P-02：资源与知识获取

学习者或公开访客发现学习资源、经验文章、项目/代码资源、外部课程/视频等。站内原创或已授权内容以文章为主要呈现形态，可含符合规则的直接插图和结构化信息区块；外部资源以经审核的摘要、来源和外链为主。资源是与竞赛、招募同等级的核心路径，不是装饰性附属内容。

### P-03：可信合作方招募

合作方通过受限、独立归属的账户提交自己名下的招募候选内容；管理员审核后公开。学习者从详情页进入受控社群或外部渠道继续沟通。平台不提供“学生公开寻找团队”的独立站内市场。

### P-04：公开内容贡献

所有公开访客（包括没有普通账户的用户）均可通过独立投稿/反馈入口提交竞赛线索、学习资源、经验、项目或改进建议。该入口与合作方申请、招募发布分开；所有贡献先审核，不能自动公开，也不开放合作方后台或校内社群。每次提交必须以中文明确反馈成功、失败或重复提交状态；双击、刷新或网络重发不得生成多条业务记录。

### P-05：合作方申请

老师、学生组织负责人、竞赛团队负责人或高可信个人，通过独立的合作方申请流程申请受限账户。账户开通不是自动注册，而是经过人工核验后的管理动作。收集必要联系方式前必须说明用途、可见角色和留存规则；提交结果必须可解释且可安全重试。

## 6. 信息架构方向

正式页面与路由由 S-05 细化；本规范先冻结信息层面的主栏目和旧入口迁移方向。

| 主栏目/能力 | 产品含义 | 旧 V0 迁移方向 |
| --- | --- | --- |
| 竞赛 | 发现、理解和核验竞赛信息 | 保留并扩展。 |
| 资源 | 学习资源、经验、文章、项目/代码及外部知识入口；站内内容采用富文本文章与受限直接图片，外部内容以来源明确的链接为主 | 从旧 V0 的排除项提升为核心栏目。 |
| 招募 | 已核验合作方发布的可信招募 | 旧 teams 的公开双向组队能力并入/替代为招募。 |
| 关于 | 项目定位、团队故事、边界、联系与必要说明 | 保留，并承载项目团队信息。 |
| 加入我们 | 顶部独立主导航；进入专门页面后提供受控的校内社群入口 | 新增独立页面；不是站内注册、入会或普通账号入口。 |
| 合作方申请 | 申请成为合作方、经审核后获得受限账户 | 新增独立路径。 |
| 内容投稿/反馈 | 提交资源、经验、项目、竞赛线索或反馈 | 与合作方申请、招募发布分离；统一提供提交反馈和重复提交保护；是否进入主导航由 S-05 裁决。 |
| 校内社群入口 | 位于“加入我们”页面；也可在符合场景的招募详情提供同一受控导流 | 旧 join 入口迁移为受控导流，不是站内入会/注册；重试与最小日志由 S-04 规定。 |

## 7. 版本与发布路线

### 7.1 阶段定义

| 阶段 | 目的 | 可以缩小的内容 | 不可被误解为永久删除的内容 |
| --- | --- | --- | --- |
| R0：治理与原型对齐 | 确认规则、原型继承、数据边界与开发方式 | 可只做资料梳理和一个垂直切片 | 不裁减正式产品范围。 |
| R1：内部工程验证 | 验证一条从管理到公开展示的完整能力链，包括富文本文章、外链、受限直接图片与防重复提交 | 可使用受控样例、少量页面和本地环境 | 不能把“只做竞赛列表”称为正式产品。 |
| R2：首批校内测试 | 用项目负责人选择的真实目标用户验证信息质量、社群导流、内容审核与可解释提交 | 不预设测试人数、合作方硬门槛或独立测试窗口；使用未来正式运营的同一套管理后台能力 | 资源、竞赛、可信招募与审核链路必须有可用实现；资源与招募各至少验证一条真实完整链路。 |
| R3：首次正式上线 | 面向既定校内范围持续运行 | 可按运营能力限制栏目数量和合作方规模 | 不能缺失关键责任边界、审核、归档、隐私、媒体存储/清理/备份和运行保障。 |
| R4：后续扩展 | 在证据充分后扩展校外、组织模型、更多互动和内容形态 | 逐项 DR 决定 | 不自动恢复被明确排除的站内社交/人才库功能。 |

### 7.2 能力进入门槛

| 能力 | R1 内部工程验证 | R2 首批校内测试 | R3 首次正式上线 |
| --- | --- | --- | --- |
| 竞赛发现与官方来源 | 一条完整样例链路 | 必须可用 | 必须可持续更新与下线 |
| 资源/文章/项目入口 | 至少验证富文本文章、受限直接图片与外链三类 | 必须可用，含审核、来源/权利说明和图片限制 | 必须可持续发布与归档，并具备经确认的媒体存储、清理与备份方案 |
| 合作方招募 | 验证合作方独立归属内容到管理员审核的闭环 | 必须可用，限可信合作方；至少有一条真实完整链路 | 必须可用，受限账户、归属转交与审核可追溯 |
| 内容投稿/反馈 | 可人工辅助处理，但须验证成功/失败反馈与重复提交保护 | 至少有可审核入口、可解释反馈、隐私告知和安全重试 | 必须有可审核入口、隐私说明及可执行留存/删除规则 |
| 校内社群导流 | 可用模拟入口验证，覆盖答题错误、网络失败和重复提交状态 | 必须有受控入口、低门槛重试与最小异常记录 | 必须有受控入口、责任边界说明、可执行日志清理与隐私规则 |
| 普通学生账号/聊天/站内报名 | 不做 | 不做 | 不做 |

R2 和 R3 的“可用”不等于规模化运营：它要求一条真实、可审核、可下线、可解释的完整路径，而不是每个栏目都有大量内容。R2 不把测试人数或合作方数量作为硬性准入指标；项目负责人从符合首批服务范围的人群中选择实际测试参与者，并在验收记录中保留非敏感测试结论。

R2 使用未来正式运营的同一套管理后台、角色和内容状态模型，不另建测试专用后台或测试入口；这不等于测试内容可以绕过审核后公开。草稿、待审核、公开、隐藏和归档仍按正常规则运行。该决定只固定产品后台能力，不预先决定本地、测试或正式部署环境，环境策略留待 S-08。

## 8. 明确不做项

截至本草案，以下能力不进入首次正式产品：

- 普通学生注册、登录、个人资料、简历和人才库；
- 站内聊天、私信、评论、点赞、好友、面试和报名流程；
- 学生公开发布“我在找团队”的双向组队市场；
- 自动化 AI 推荐、复杂匹配评分和站内即时社交；
- 将 QQ/微信社群中发生的沟通、筛选、面试或报名过程保存为平台业务数据；
- 为了追求“生态”而无边界地接入校外人员、组织或私密联系方式。
- 视频托管、网盘代存、任意文件上传、自动抓取第三方文件、自动导出或转载工具；这些能力可在未来按 DR 评估，不是首发默认范围。

这些能力未来能否出现，必须按 S-01 建立 DR；“后续可能做”不能改变当前不做的实现边界。

## 9. 与旧 V0 的关键裁决

| 旧资料方向 | 本草案方向 | 处理原则 |
| --- | --- | --- |
| 仅面向校园竞赛信息与双向组队 | 面向校内学术生态，竞赛是入口之一 | 以本草案的产品定位为候选当前基线。 |
| 资源不进入 V0 | 资源为同等级核心路径 | R2 前必须有可用资源链路。 |
| teams 同时承载团队招人和学生找团队 | 招募仅面向可信合作方；学生需求在社群处理 | 旧 teams 页面不按原语义保留。 |
| submit 泛化为站内投稿 | 内容投稿保留，但与合作方申请/招募分开 | 投稿不等同于合作方账户申请。 |
| join 是普通入口 | 社群入口受校内低门槛验证控制 | 不变成站内注册/报名。 |
| 绿色强调卡片实现 | 浅色、克制、Notion 风格原型为视觉参考；内容录入不再以固定表单卡片作为最终体验，而采用“结构化元数据 + 富文本文章正文” | S-05 和 B-001 负责像素、组件和编辑交互落地。 |

| ID | 已确认结论 | 影响 |

上述结论已获项目负责人整体批准，并随第 2 批合入 docs/main，现为团队当前规范性产品基线。它们约束后续规格和模块，但不得跳过 S-05 至 S-08、模块开工卡及 S-02 的协作要求而直接扩大实施范围。

## 11. 已满足的批准条件

S-03 已满足以下批准条件：

1. 产品定位不是“永久竞赛 MVP”，而是以阶段交付实现校内学术生态；
2. 资源、竞赛和可信招募的相对优先级；
3. 普通用户与网站/社群的责任边界；
4. 首次正式服务范围和校外公开内容边界；
5. R1、R2、R3 的定义及明确不做项；
6. 已回填的 DR-001、DR-002、DR-003、DR-004 与产品范围、网站/社群边界不冲突；
7. 本批五项答辩结论、DR-004 语言策略及其与既有 DR 的边界已正确回填；第 2 批只剩整体最终审阅与合并决定。
