## 1. 目的与边界

本规范定义从 M0 开工卡到 M4 收口之间，代码怎样保持可读、可验证、可复现和可维护。它解决的不是“选什么框架”，而是每个已批准模块至少要交付哪些工程证据：改动边界、类型、状态、测试、人工验收、已知限制与 Git 记录。

它适用于正式代码仓库 `D:\Projects\voidhaven` 的前端及未来同仓或关联服务代码。当前 Vite、React、TypeScript、npm、ESLint、Vitest 和 Playwright 配置是现实起点，不因为本规范出现就自动升级依赖、增加 CI、创建后端、改造目录或运行命令。

本规范不选择云厂商、数据库厂商、身份供应商、对象存储、域名、生产凭据或部署平台；这些外部/运行决定由 S-08 和单独确认处理。它也不替代 S-03 至 S-06 的产品、隐私、页面和 API 规则。

### 2.2 不可妥协原则

1. **规格先于实现。** 代码不得自行扩大产品、账号、隐私、数据或外部服务范围；有冲突先停下并按 S-01/S-02 处理。
2. **模块先于批量改造。** 每次候选改动必须属于已批准 M0 的文件与验收范围；“顺手重构”需要单独写入卡或获得确认。
3. **边界先于便利。** 页面不直接相信 URL、前端角色或数据库对象；组件经 Service/Mapper 消费 S-06 的稳定展示模型。
4. **安全失败优于静默成功。** 类型、校验、权限、幂等、版本冲突、来源/语言/权利缺口和受控入口失败必须可识别、可解释、可测试。
5. **最小变更优于整仓格式化。** 不因一个功能而自动重排无关文件、升级无关依赖、删除旧文件或覆写用户改动。
6. **可复现优于口头声称。** 每个候选模块提供实际命令结果、人工验收步骤和已知限制；“理论上可运行”不是验证。

## 3. 代码边界与目录责任

下表是当前目标职责，不强制在未批准模块中迁移全部目录。新文件应优先落在相应边界；如果新领域需要不同组织方式，先在模块卡说明。

| 位置 | 责任 | 不应承担的责任 |
| --- | --- | --- |
| `src/App.tsx`、`src/layouts/` | 路由树、共享布局、全局可访问性壳层和页面入口 | 页面业务查询、权限绕过、硬编码私密链接。 |
| `src/pages/` | 一个可访问路由的页面组合、页面级状态与用户可见文案 | 直接拼接 HTTP/数据库、跨页面复制同一业务映射。 |
| `src/components/` | 可复用的呈现、交互和语义状态组件 | 私自拥有跨页面业务状态、绕过 Service 读取 Mock。 |
| `src/services/` | 前端稳定领域接口、HTTP/Mock Adapter、DTO Mapper 和查询/提交边界 | React 渲染、数据库实体透传、把私密管理对象下发给公开组件。 |
| `src/mock/` | 受控本地 Fixtures、可预测的错误/空态/延迟和同一 Service 契约的 Mock 实现 | 伪造学生账号、私人联系方式、生产密钥或绕过 S-04 生命周期。 |
| `src/types/` | 跨页面/Service 的领域与展示类型 | 不经 Mapper 直接等同后端表、临时 `any` 垃圾桶。 |
| `src/hooks/` | 可复用状态、异步、焦点或视图行为 | 隐藏全局业务规则、吞掉错误或产生不可测试副作用。 |
| `src/test/`、同目录 `*.test.tsx` | 测试设置、可重复断言与测试工具 | 代替人工验收、承载生产业务逻辑。 |
| `e2e/`（未来） | 浏览器级关键路径与回归证据 | 覆盖每个实现细节，或替代单元/组件测试。 |

## 4. 实现与编码规则

### 4.1 TypeScript、React 与命名

- 新增/修改应用代码使用 TypeScript；保留现有编译器的未使用检查，不以注释或宽泛类型压制真实问题。
- 不使用裸 `any`、不安全类型断言或 `@ts-ignore` 逃避契约；确有边界输入时先用未知值、收窄、校验或显式的可解释豁免，并在同一模块说明原因。
- React 组件、类型、枚举使用 PascalCase；函数、变量、字段使用 lowerCamelCase；文件名、导出和其主要职责保持一致。代码内部可以使用英文标识，用户可见文案按 S-03/S-05 使用简体中文。
- 组件接受清晰的 Props，页面负责组合；可复用状态必须有显式 Loading、Success、Empty、Error 或等价受限状态，而非隐式 `null`。
- 未出现明确重复和复杂度证据前，不引入全局状态库、事件总线、复杂依赖注入或抽象层；局部 React 状态与 Service 边界优先。

### 4.2 Service、DTO 与错误处理

- 组件和页面不得直接调用 `fetch`、导入 fixture 或假设数据库字段；通过 `src/services/` 的领域接口访问 Mock/HTTP 实现。
- S-06 的 API DTO、前端展示模型和内部管理模型分别表达；公开组件不得获得私密联系方式、审核意见、令牌、群二维码、完整匿名答案或未审核内容。
- 错误处理必须保留 `retryable`、安全错误语义和用户下一步；不得把后端堆栈、SQL、完整请求体或密钥展示给用户或写入常规日志。
- 幂等、并发版本、404 隐藏语义、受控入口 `no-store`、富文本和媒体限制不得只在前端实现；前端只负责正确发起和呈现 S-06 的契约结果。

### 4.3 依赖、配置与文档

- 包管理器固定为 npm；新增、删除或升级运行时依赖必须说明功能必要性、许可证/维护风险、包体积或安全影响，并同时审阅 `package.json` 与 `package-lock.json`。
- 不安装与已批准模块无关的 UI 库、认证 SDK、分析 SDK、云 SDK 或生成工具；外部服务选择需要项目负责人单独确认。
- `.env`、`.env.*`、密钥、私钥、生产 URL、数据库备份和真实个人数据不得提交。只允许提交不含真实值的 `.env.example`，且新增变量要在 S-08/模块说明中写用途、环境和是否敏感。
- `README.md` 不再长期保留脚手架说明时，应在一个已批准模块内替换为本项目的运行、测试、目录和安全入口说明；不能混入功能无关的营销或个人日志。

### 4.4 格式、提交与审阅

- 每个候选提交前至少查看目标 diff、运行适用检查，并按 S-02 使用清晰模块 ID 的小提交；禁止 `git add .`。
- `npm run format` 是检查命令；如格式化需要改写大量无关文件，应暂停并拆分为单独、可审阅的格式化模块，而非混入功能提交。
- 代码审阅至少检查：是否符合已批准 S/DR、是否扩大数据/权限、是否泄露敏感信息、异常/空态是否可达、测试是否证明行为、依赖/配置是否有意外变化。
- 当前未授权配置 GitHub Actions、第三方 CI 或远程分支保护。批准前的质量门槛可以先由本地实际命令和人工验收记录承担。

## 5. 测试策略与最低证据

### 5.1 分层目标

| 层级 | 适用内容 | 至少要证明什么 |
| --- | --- | --- |
| 静态检查 | 所有 TypeScript/React 候选改动 | `npm run format`、`npm run lint`、`npm run build` 的实际结果，或不能运行时的明确原因。 |
| 单元测试 | Formatter、Mapper、Service、状态转换、筛选、排序、幂等键和纯函数 | 正常值、边界值、未知 ID/空值、错误/冲突等核心规则。 |
| 组件测试 | 页面、卡片、表单、导航、状态面板 | 用户可见文案、语义角色、链接、键盘行为、Loading/Empty/Error 以及不泄露字段。 |
| 端到端测试 | 跨路由或高风险公开/受限路径 | 从可见入口到安全结果的真实浏览器流程；桌面与移动至少覆盖受影响关键路径。 |
| 人工验收 | 视觉、响应式、可访问性、产品语义 | 与 M0 卡逐项对照，记录浏览器/宽度、步骤、结果、风险和未覆盖部分。 |

### 5.2 必测情形

每个模块不必机械覆盖全站，但只要影响下列情形，就必须有相应测试或人工验收：

- 公共页面：Loading、Success、Empty、Error、Not Found、长标题、缺失可选字段、移动端和键盘导航；
- 写入/表单：字段校验、重复提交、网络失败安全重试、错误可修正性、私密字段不回显；
- 权限/受限操作：未登录、无权、对象归属、隐藏资源 404、角色不能由前端参数伪造；
- 内容/媒体：来源、语言、权利缺口，禁止的图片/富文本输入以及公开 DTO 不含二进制/私密值；
- 生命周期：到期三天、隐藏/归档、配额冲突、管理员动作审计和相关公开表现。

### 5.3 测试数据纪律

- Fixture 使用明显虚构、可公开的名称、链接和内容；禁止复制真实私人联系信息、社群二维码、口令、凭据或未经许可的完整文章。
- 测试中构造的资源、竞赛和团队招募仍应遵守 S-03 至 S-06 的字段、来源、语言和隐私边界。
- 测试不得依赖本机当前时间、真实互联网、真实账户或先前测试的副作用；必要时固定时钟、请求和随机值。
- 测试报告、截图、trace、coverage 和构建产物均按 `.gitignore` 管理，不自动上传或提交。

## 6. 模块质量门与完成定义

### 6.1 M0 至 M4 的工程交付

| 阶段 | 必须具备的质量信息 |
| --- | --- |
| M0 | 已批准规格/DR、文件影响、风险、学习模式、测试想法、人工验收、停止条件和候选分支。 |

### 6.2 候选合并的最低质量清单

1. 模块范围未超出已批准 M0；
2. 所有受影响的 S-03 至 S-06 规则可在代码/测试/人工验收中追溯；
3. `format`、`lint`、`test`、`build` 的适用结果已实际记录，失败没有被掩盖；
4. 路由、错误、空态、移动端、键盘和私密数据边界已按受影响范围验收；
5. 新依赖、环境变量、数据迁移、外部服务与未解决风险被单独说明；
6. 项目负责人明确给出代码 main 的合并决定。
