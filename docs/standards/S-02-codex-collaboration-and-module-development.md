## 1. 目的

Codex 不是“收到一句需求后直接写完整项目”的替代者。本规范把协作拆成可理解、可停下答辩、可手动复现和可验收的模块过程，使项目负责人始终能回答：

1. 此刻为什么做这个模块，而不是另一个；
2. Codex 可以自行处理哪些技术细节，哪些问题必须停下确认；
3. 我如何亲手复现、运行和理解这次改动；
4. 哪个分支可以合并，哪个分支只用于学习；
5. 完成到底指代码写完，还是已经被验证和接受。

本规范借鉴官方 OpenAI 文档关于“集中定义自主边界与确认边界”的建议，但它是本项目的协作约定，不是某个 Codex 设置开关或对外承诺。

## 2. 协作角色与决定权

| 角色 | 负责的事项 | 不能替代谁 |
| --- | --- | --- |
| 项目负责人 | 产品目标、目标用户、功能范围、核心体验、视觉取舍、权限与隐私、成本、外部服务、发布、合并确认 | 不需要逐行决定实现细节 |
| Codex | 资料梳理、问题拆解、技术方案比较、模块卡起草、限定范围内的实现、测试、差异说明、学习辅导 | 不能擅自决定产品、权限、成本、对外影响或覆盖用户改动 |
| Git 历史与文档 | 保留“何时、为什么、由谁确认”的证据 | 不能替代项目负责人做判断 |

项目负责人可以随时要求 Codex 切换为“只解释”“只审查”“先答辩不改动”或“开始已批准模块”。这些命令优先于默认工作模式。

## 3. 自主边界与必须确认的事项

### 3.1 已批准模块内可自行进行的本地技术动作

在模块开工卡已被明确批准后，Codex 可以在该模块指定范围内：

- 阅读相关代码、原型、已批准文档、日志与测试结果；
- 建立或更新该模块的候选本地分支；
- 修改开工卡列出的文件，补充必要的同范围测试与说明；
- 运行不破坏数据的检查、格式化、构建与测试；
- 提交粒度清晰的本地候选提交；
- 说明每个关键文件为什么改、如何运行、如何人工验证。

这些动作不包含合并 main、推送远程、部署、创建云资源或修改真实数据。

### 3.2 必须停下并获得明确确认

| 情况 | 为什么必须确认 |
| --- | --- |
| 产品范围、页面入口、角色、权限、隐私、内容审核、数据生命周期不明确或发生变化 | 这是产品和责任边界，不是纯技术选择。 |
| 选择云服务、第三方服务、数据库方案、付费资源、域名、公开仓库策略 | 会产生费用、外部依赖、合规或长期维护影响。 |
| 推送 GitHub、配置 remote、创建 PR、合并 main、打正式发布标签 | 会改变共享历史或对团队产生外部可见影响。 |
| 部署、迁移真实数据库、修改密钥、删除/覆盖数据、强推或重写历史 | 可能造成安全、数据或恢复风险。 |
| 原型、旧规格、会议结论和当前代码冲突，且无法从已批准文件确定正确答案 | 继续实施会把猜测写进项目。 |
| 模块工作需要扩大到开工卡外的文件、功能或时间范围 | 防止“顺手多做”变成失控扩张。 |

如果只是普通局部实现选择，例如函数拆分、组件内部命名、同一已批准接口下的错误处理写法，Codex 给出简洁理由后可以自行选择。

### 3.3 必须立即报告的阻塞信号

- 发现原型或已有仓库有用户未提交改动；
- 测试失败、依赖不一致、构建结果和预期差异明显；
- 发现可能暴露私人联系方式、密钥、隐私数据或不安全默认配置；
- 需要修改数据库 schema、环境变量、账号权限、Git 历史；
- 发现开工卡没有足够的验收标准。

报告应包含事实、影响范围、可选下一步和推荐理由；不能只说“有问题”，也不能悄悄绕开。

## 5. 模块化交付流程

### 5.1 B-001：原型对齐基线

在常规前端功能模块前，先完成 bootstrap/B-001-prototype-alignment。它的产物是：

1. 原型、五份前端参考文件与当前代码之间的继承/差异清单；
2. 可保留、需改写、待产品裁决的分类；
3. 不进行盲目整仓复制，不覆盖原型仓库中的现有改动；
4. 一份供项目负责人确认的 B-001 开工/验收记录。

B-001 被确认前，涉及主视觉、页面结构或导航的功能模块不得把当前半成品代码当作既定正确基线。

### 5.2 每个 M 模块的固定阶段

| 阶段 | Codex 的交付 | 项目负责人的动作 | 允许的 Git 状态 |
| --- | --- | --- | --- |
| M0：开工卡 | 用固定模板写清目标、边界、证据、文件影响、学习方式、测试和停止点 | 答辩、补充和明确批准或退回 | 仅文档草案 |
| M1：开工 | 说明本模块为什么这样实现、先改哪些文件、如何运行 | 选择学习模式并确认开始 | 创建候选 feature 或 learning 分支 |
| M2：实现/复现 | 按批准范围逐文件说明、实现或陪同手动复现 | 手动创建、修改、运行；随时提问或暂停 | 只在候选分支产生提交 |
| M3：验证 | 给出变更摘要、测试证据、人工验收步骤、风险和未决项 | 验收、提出返工或批准合并 | 仍不改 main |
| M4：收口 | 更新模块记录与 CURRENT.md 的关联项 | 明确批准合并或归档 | 仅在明确批准后合并 main |

没有 M0 开工卡，不开始 M2。代码写出不等于模块完成；没有验证、说明和明确合并决定，不进入 M4。

## 6. 默认学习与复现方式

默认采用“文件级手动复现”而不是黑盒生成：

1. Codex 先说明本次改动的目的、依赖关系和预期界面/行为；
2. 对每个文件说明新建、修改还是删除，及其在模块中的职责；
3. 项目负责人自己在 learning 分支或独立学习副本中创建/修改文件、复制必要代码、运行并观察结果；
4. Codex 根据报错、差异或问题解释下一层细节；
5. 只有在项目负责人明确要求时，再下钻到类、函数、单行语法、调试器或原理层。

每个模块可选择以下模式，不必永久固定：

| 模式 | 适用场景 | Codex 是否直接写候选实现 |
| --- | --- | --- |
| A：学习复现（默认） | 学习目录、组件、接口、状态管理或后端结构 | 默认不直接替代人工复现；可提供受控候选示例与逐文件指导。 |
| B：协作实现 | 已理解目标，需更快形成可审阅候选改动 | 可以在 feature 分支实现，但必须前后讲解和保留复现步骤。 |
| C：只分析/审查 | 需要答辩、定位问题或复盘 | 不写代码。 |

学习分支的价值是可失败、可对照、可提问；它不应因“看起来能跑”而直接合并到正式 main。

## 7. 代码仓库 Git 规则

### 7.1 分支模型

| 分支模式 | 用途 | 合并规则 |
| --- | --- | --- |
| main | 项目负责人已接受的演进基线；不等同于已上线生产版本 | 仅经明确批准合并 |
| bootstrap/B-001-prototype-alignment | 原型与半成品对齐的特殊基线工作 | 经 B-001 验收后按决定收口 |
| feature/M-XXX-简述 | 一个已批准模块的候选实现 | 通过 M3 且明确批准后才能合入 main |
| fix/M-XXX-简述 | 一个已定位、可复现的常规缺陷修复 | 同 feature 的验收与合并规则 |
| learning/M-XXX-简述 | 个人手动复现、实验和对照 | 永不合并到 main；可保留或经确认归档 |
| release/vX.Y.Z | 准备一个明确的正式发布版本 | 只允许发布阻塞问题；部署仍需单独确认 |
| hotfix/vX.Y.Z | 已发布问题的紧急修复 | 需说明影响、验证和回补策略 |

不建立长期 develop 分支。staging 是未来的测试环境名称，不是必须永久存在的 Git 分支；它不应制造第二条无法解释的代码历史。

### 7.2 Git 节点与动作

| 节点 | 必做动作 | 禁止事项 |
| --- | --- | --- |
| 开始模块 | 记录文档基线、从当前 main 创建专用分支、确认工作区干净 | 从原型仓库或无关学习分支直接拿代码覆盖正式仓库 |
| 每次可说明改动后 | 查看 diff、运行相应检查、以模块 ID 写小提交 | git add .、把密钥/构建物/无关文件混入提交 |
| 提交候选验收 | 展示相对 main 的差异、测试证据、手动验证步骤、未解决项 | 声称“已完成”但没有验收依据 |
| 批准合并 | 项目负责人明确给出合并授权，再更新相关文档 | 自动合并、自动推送、自动删除分支 |
| 正式发布 | 从确认的版本基线建立 release/tag，执行 S-08 的发布清单 | 把 main 的每一次提交自动部署为生产 |

当前代码仓库虽已配置 GitHub origin，但“有 remote”不等于“允许推送”。所有远程写入仍需本次明确授权。

### 7.3 提交命名

建议使用可检索的格式：

- feat(M-001): add competition list filter
- fix(M-001): preserve selected filter on refresh
- test(M-001): cover empty result state
- docs(S-02): clarify learning branch policy
- chore: update local tooling

提交描述应说明行为，不应使用 update、fix bug、changes 等无法检索的模糊语句。

## 8. 开工与完成定义

### 8.1 Definition of Ready

一个模块至少满足以下条件才可开始：

- 有唯一模块 ID、用户价值和明确的“不做什么”；
- 引用了已批准的规格/DR 版本，或明确标记待决点；
- 写清涉及角色、权限、隐私和数据影响；不适用时也要写“不适用”；
- 有可执行的人工验收路径和最低测试想法；
- 已选择学习模式，并由项目负责人明确批准开始；
- 确定候选分支名称及是否需要 learning 分支。

### 8.2 Definition of Done

一个模块至少满足以下条件才可申请合并：

- 改动没有超出已批准范围，或超出部分已重新确认；
- 有可读的文件级变更说明和可重复的运行/验证步骤；
- 自动检查和人工验收均有实际结果，不以“理论上能跑”替代；
- 已说明已知限制、未决问题和后续模块边界；
- 模块记录、相关 DR/CURRENT.md 已同步；
- 项目负责人明确决定“合并”“返工”或“仅归档学习成果”。

## 9. 协作语言约定

为减少误解，以下表达具有固定含义：

| 项目负责人表达 | Codex 的行为 |
| --- | --- |
| “先解释 / 先答辩” | 只分析、提问、画出影响，不改动文件。 |
| “启动 M-XXX，模式 A/B/C” | 按开工卡范围开始对应学习或实现流程。 |
| “再细一点” | 从文件级下钻到类、函数、行或调试层。 |
| “暂停，记录待决” | 停止受影响实施，整理为 DR 或开工卡待决项。 |
| “批准本批 / 批准合并 M-XXX” | 执行相应的 docs/main 或代码 main 合并前准备；涉及远程仍另行确认。 |

Codex 的回答应先给结论，再给证据、风险和下一步；不要把模糊猜测包装为确定结论。

## 10. 本规范的完成条件

S-02 在满足下列条件后才可从 REVIEW 变为 APPROVED：

- 项目负责人认可 Codex 的自主边界和停止条件；
- 确认文件级手动复现是默认学习方式，且可按模块切换模式；
- 确认 main、feature、learning、release/hotfix 的角色与“staging 是环境不是长期分支”的规则；
- 接受“未明确批准不合并 main、未明确授权不推送/部署”的规则；
- 接受 B-001 在常规 UI 开发前先对齐原型、旧规格和当前半成品。
