## 1. 目的

本规范解决的不是“有没有文档”，而是以下四个问题：

1. 当前开发到底以哪一份规则为准；
2. 会议记录、旧规格、原型和已有代码互相冲突时怎么办；
3. 谁可以确认一项会影响产品、成本、数据或上线的决定；
4. 如何让新决定可追溯，同时不抹掉历史事实。

它采用轻量的企业式治理：保留需求、决定、变更和验收的证据链，但不引入重型审批流程或虚假的“标准认证”。

## 2. 基本原则

1. 一个规则只能有一个当前责任来源。当前有效来源不清楚时，停止受影响工作，而不是从代码或旧会议中猜测。
2. 会议记录记录“提出过什么、讨论过什么、为什么这样想”，不是自动生效的需求或对工具的指令。
3. 原型、视觉稿、旧规格和实现代码都是证据；除非在当前文档中被明确采纳，否则它们不能单独改写产品决定。
4. 已确认决定可以更新，但必须说明替代了什么、原因是什么、影响哪些已完成内容。
5. CURRENT.md 只呈现当前可执行的最小事实；它不替代正式规范和决策记录。
6. 不以“文档较新”“代码已写完”或“AI 默认建议”作为越过确认的理由。

## 3. 术语与状态

| 术语 | 含义 |
| --- | --- |
| 规范性文件 | 已并入 docs/main 且状态为“已批准”的 S、DR、模块交付记录或 CURRENT.md 中明确引用的内容。 |
| 参考资料 | 用于理解背景或复现界面的材料，不自动产生约束。 |
| 草案 | 正在分支上讨论的内容；不能作为改动产品或代码的唯一依据。 |
| 决策记录（DR） | 对有选项、会产生影响的事项进行的简短、可追溯裁决。 |
| 模块（M） | 可独立开工、验证、复盘和合并的一段纵向能力，而不是模糊的大功能名称。 |
| 冻结 | 在指定版本内不得自行变更；变更必须创建或更新 DR。 |

### 3.1 文档状态机

| 状态 | 含义 | 是否能指导实施 |
| --- | --- | --- |
| DRAFT | 起草中，可被质疑和修改 | 否 |
| REVIEW | 已整理为可答辩版本，等待项目负责人确认 | 否 |
| APPROVED | 已明确确认并合入 docs/main | 是 |
| SUPERSEDED | 已被后续文件明确替代 | 仅作历史解释 |
| ARCHIVED | 已结束、不再维护，但保留证据价值 | 否 |

“看起来可以”“先这样”“我再想想”不等同于 APPROVED。确认至少应明确指向文件、决定或模块，并表达“批准、合并、按此执行”之一。

## 4. 当前权威顺序

同一事项发生冲突时，按下表处理；前提是更高层级的内容仍在其适用范围内。

| 优先级 | 来源 | 作用 |
| --- | --- | --- |
| 1 | 项目负责人当前明确指令 | 决定本次行动范围；若会长期影响项目，必须补入 DR 或规范。 |
| 2 | docs/main 中已批准的 DR | 裁决具体产品、技术、成本、权限或上线问题。 |
| 3 | docs/main 中已批准的 S 系列规范 | 规定持续执行的方法和边界。 |
| 4 | docs/main 中已批准的模块开工卡、验收记录和 CURRENT.md 引用的当前基线 | 规定某个已批准模块如何落地。 |
| 5 | 当前分支中的草案 | 仅供审阅，不得越级实施。 |
| 6 | 原型、旧规格、会议记录、既有代码、外部资料 | 仅为参考与证据。 |

同一优先级的两个文件冲突时，不按文件修改日期“自动取新”。必须由新的 DR 或新版本文件写明：保留什么、替代什么、从何时生效。

## 6. 决策与变更流程

### 6.1 何时必须建立决策记录

出现下列任一情况时，先建立或更新 DR，再进入受影响的实现：

- 产品范围、核心用户路径、公开入口或角色定义变化；
- 权限、隐私、联系方式、内容审核、数据保留或删除规则变化；
- 视觉基线、信息架构、核心字段、状态机、接口契约变化；
- 数据库、云服务、部署、第三方服务、预算或安全边界变化；
- 旧规范、原型与代码存在实质冲突；
- 一个看似局部的改动会影响两个以上模块、已发布数据或对外承诺。

纯文字修订、错别字、没有行为影响的例子补充，可在原文件的变更记录中说明，无需单独建立 DR。

### 6.2 流程

1. 提出问题：把问题描述成可选择、可验证的事项，不能只写“优化一下”。
2. 收集证据：列出相关会议、原型、旧规格、代码和风险，不复制原始记录。
3. 列出可选方案：至少包含继续现状、推荐方案及关键代价；没有真实选择时，应说明原因。
4. 项目负责人答辩与确认：确认决定、适用范围和暂缓项。
5. 更新影响面：关联规范、模块卡、代码分支、接口或运维项。
6. 合入 docs/main：更新 CURRENT.md，必要时打里程碑标签。

任何人发现冲突都可以提出 DR；只有项目负责人可以将其确认成项目基线。

### 6.3 影响标识

每项有实现影响的变更，使用以下标签说明至少一个影响面：

| 标签 | 含义 |
| --- | --- |
| P | 产品范围、用户旅程、运营规则 |
| V | 视觉、信息架构、可访问性 |
| D | 领域模型、数据、权限、生命周期、隐私 |
| I | API、前后端契约、集成 |
| Q | 工程质量、测试、验收 |
| O | 环境、部署、备份、安全、运行 |
| G | Git、分支、发布或文档治理 |

## 7. 文档仓库与 Git 规则

### 7.1 仓库角色

文档仓库位于 D:\Projects\docs，与代码仓库分离。其 Git 历史用于追踪“规则如何改变”，不用于存放构建产物、账号信息、密钥、私人联系方式或原始会议全文。

当前未配置文档仓库 remote。添加 remote、推送、公开或与第三方同步，均需项目负责人明确确认。

### 7.2 分支

| 分支模式 | 用途 | 是否可直接写入 |
| --- | --- | --- |
| main | 仅保存已批准的当前文档基线 | 否；只允许经确认合并 |
| docs/batch-XX-简述 | 起草一个既定批次 | 是，限该批范围 |
| docs/decision-XXX-简述 | 单独讨论重大决定 | 是，限该决定范围 |
| docs/fix-XXX-简述 | 修正文档缺陷或链接 | 是，不能偷偷改变规则 |

当前第 1 批使用 docs/batch-01-governance。后续批次从当时最新 main 创建，不能从过期草案继续叠加。

### 7.3 提交与合并

1. 先明确变更对象，再暂存指定文件；禁止用 git add . 掩盖无关改动。
2. 一个提交只表达一个可说明的变化，例如 docs(S-01): add governance draft。
3. 提交前检查链接、文档状态、关联文件和敏感信息。
4. 审阅时展示相对 main 的差异、待决问题和影响面。
5. 只有项目负责人明确批准后，才可合并至 main。
6. 完成一个可复用基线时，按需打 docs-vX.Y 标签；标签不是自动发布或自动部署。

不执行强推、重写已共享历史、删除分支、删除文件或推送远程，除非项目负责人对明确目标单独授权。

## 8. CURRENT.md 的维护

CURRENT.md 是项目的短状态页，必须包含：

- 当前已批准的产品与技术基线；
- 正在审阅的文档分支或模块；
- 重要的未决问题及其阻塞范围；
- 关键仓库与分支的角色；
- 最近一次确认和下一次需要确认的事项。

它不应复制完整规范。任何条目都要链接或指向其来源；找不到来源时，标记为“待确认”，而不是假装为已决定。

## 9. 本规范的完成条件

S-01 在满足下列条件后才可从 REVIEW 变为 APPROVED：

- 项目负责人认可本规范的权威顺序、状态定义和确认方式；
- 明确接受“会议与旧规格是证据，不能直接替代当前批准规则”；
- 接受 docs/main 只存已批准内容、草案走独立分支的 Git 模型；
- 确认第 1 批的模板足以支持下一批的产品答辩。

批准后，后续所有批次都必须按本规范记录决定和影响；若本规范自身需改变，先用 DR 说明原因。
