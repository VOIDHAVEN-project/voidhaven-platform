## 1. 用户价值与完成结果

B-001 先把“已批准的产品与界面规则”落实为正式代码仓库可继续开发的**对齐基线**，避免后续竞赛、资源、团队招募或投稿模块分别沿用旧原型的 `/teams`、学生找队、缺少资源栏目等过期含义。

完成时，项目负责人应能在 `D:\Projects\voidhaven` 的候选分支中观察到：

1. 全局路由、Header、Footer 和首页使用 S-05 的公开信息架构：竞赛、资源、团队招募、投稿/反馈、加入我们、关于；
2. 首页桌面端呈现“近期竞赛 / 团队招募”双栏，再以同级全宽区呈现学习资源；移动端顺序为竞赛、资源、团队招募；
3. 旧 `/teams`、学生找队和“寻找队伍”不再被当作新的公开产品语义；新的正式路径为 `/recruitments`；
4. 前端领域/Mock 边界开始按 S-06 使用 Competition、Resource、Recruitment 的公开展示模型，而不是继续把旧 `TeamService` 当作产品基线；
5. 原始浅色、克制、Notion 式信息关系被有选择地继承，而不是整仓复制原型或覆盖用户已有改动。

这不是“把所有 S-05 页面一次做完”的模块。它只建立路由、视觉、首页和 Mock 边界的可继续开发基础；完整资源详情、投稿实际提交、合作方/管理员工作台、鉴权、图片上传和真实 API 均留给后续已批准模块。

### 4.2 角色、权限与隐私

- 公开访客只能看到经过 Mock 公开投影的竞赛、资源和团队招募；B-001 不引入普通学生账户。
- 合作方、管理员、登录、审核和配额只保留为受限路由/组件边界的预留，不在公开 Header/Footer 出现，也不实现其真实功能。
- 不在 Mock、页面、配置或测试中新增私人微信、QQ、手机、私人邮箱、群二维码、站内报名、简历或聊天数据。
- `加入我们` 的最终校内社群验证遵循 S-04/S-06；B-001 只保留安全的路由边界和文案位置，不写入真实入口。

### 4.3 数据、状态与生命周期

- 前端展示模型按 S-06 的公开投影分为 Competition、Resource、Recruitment；公开内容只由适合的 Mock Service 返回。
- 竞赛/团队招募的结束、隐藏和公开三天规则不由页面本地猜测；B-001 仅消费由 Service 提供的安全公开状态。
- 每个首页栏目独立覆盖 Loading、Success、Empty、Error；页面级 404、受限页面 Unauthorized/Forbidden 的语义由后续模块按 S-05/S-06 补齐。
- 首批 B-001 Mock 不承担真实 API、持久化或匿名投稿职责；未来 HTTP 替换必须保持 S-06 约定的 Service/Mapper 边界。

### 4.4 响应式与可访问性

- 桌面壳层、轻边框、近黑文字、英文展示字与中文无衬线 UI 字作为视觉关系，而非逐像素复制目标；
- 必须保留语义 `header`、`nav`、`main`、`footer`、标题层级、键盘菜单、可见焦点与跳至主要内容；
- 首页移动端严格验证“竞赛、资源、团队招募”顺序，不出现横向滚动或仅靠悬停可见的关键操作；
- 所有新状态面板、卡片和链接须具备可读文字，外部/受控入口不得在静态 DOM 中泄露私密地址。
