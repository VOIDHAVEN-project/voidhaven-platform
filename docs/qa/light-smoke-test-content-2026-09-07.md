## 一支队伍需要哪些技术能力

- 机械组负责结构设计、加工装配、散热、防护和快速维修。
- 电控组负责嵌入式程序、传感器、执行器、通信链路和整车状态管理。
- 视觉与算法组负责目标识别、定位、运动预测、自动瞄准和自主决策。
- 运营组负责项目管理、物料、宣传、赛务沟通和团队知识传承。

这些分工不是孤岛。视觉算法的输出频率会影响电控策略，云台结构的刚度会决定识别结果能否转化为稳定命中，电源与散热设计又会限制算法算力。成熟队伍会用统一接口、日志格式、版本规则和测试场景把这些工作连接起来。

## 新队伍的备赛顺序

1. 通读当季规则，建立“允许、禁止、待确认”问题清单。
2. 先做最小可运行底盘和可靠通信，再逐步叠加复杂能力。
3. 为关键模块定义可测指标，例如定位漂移、识别延迟、通信丢包率和连续运行时间。
4. 建立硬件台账、代码仓库、变更记录和故障复盘制度。
5. 尽早进行整车联调与对抗演练，避免各小组只在自己的环境中验证。

# ICPC 2026–2027 区域赛参赛索引

> ICPC 过去常被中文社区称为“ACM-ICPC”。各区域站的报名窗口、参赛名额和现场安排不同，本文不提供未经官方确认的中国赛区截止日期。

ICPC 是面向高校学生的团队程序设计竞赛。标准区域赛由三名学生组成一队，在五小时内共用一台计算机解决一组算法问题。它考查的不是某一种语言的熟练度，而是团队能否完成建模、证明、实现、调试和时间分配的完整闭环。

**【配图位置 1：ICPC 官方区域赛页面或赛场照片】**

## 基本赛制

- 每队通常由三名符合资格的学生组成，并由学校教练完成组织或确认。
- 标准比赛时长为五小时，三名队员共享一台工作站。
- 排名首先比较通过题目数量；通过数量相同时，再按规则比较累计用时和错误提交带来的罚时。
- 官方至少支持 Java、Kotlin、Python 3、C 和 C++，具体版本及额外语言由赛站环境决定。

稳定得分依赖团队协作。开场读题应尽快判断题目难度、知识点和实现风险；编码过程中要避免三个人同时围绕一道题低效讨论；发生错误提交后，应先通过构造反例定位问题，再决定继续修复还是切换题目。

## 2026–2027 赛季资格要点

参赛者需要在学位项目中保持规定的在读状态。常规资格还会结合开始接受高等教育的年份或出生年份判断；官方规则列出的基础条件包括 2022 年或之后开始高等教育，或出生于 2003 年或之后。参加区域赛和全球总决赛的历史次数也会影响资格，特殊情况可按规则申请资格审查。

不要只根据年龄或年级自行判断。最终应由本人、教练和学校依据 ICPC 当季规则逐项核验，并关注资格例外申请的时间要求。

## 报名与赛区

ICPC 不是所有队伍在同一个统一日期报名。区域、赛站和学校选拔可能分别设置时间表。建议按以下顺序处理：

1. 找到本校 ICPC 教练或程序设计竞赛负责人。
2. 在 ICPC 官方区域赛页面确认目标赛区与赛站。
3. 阅读承办校发布的名额、注册、缴费、设备和现场要求。
4. 在学校内部选拔前完成组队和资格预检。
5. 报名后继续检查系统状态，确保三名队员和教练信息完整。

## 我们要解决的问题

长流程 Agent 在执行真实任务时，常因中间一步判断错误、工具返回异常或上下文累积偏差而失败。重新训练模型成本高，而只增加提示词又很难稳定泛化。公开命题希望系统能从少量历史执行轨迹中学习经验，在相同或相近任务上提高成功率，并逐步减少不必要的步骤和令牌消耗。

命题页面提出的验证方向包括：以 HarmonyOS 手机作为测试平台，在不超过 5 条历史轨迹的条件下学习，并在特定任务上争取达到不低于 90% 的成功率；随着轨迹增加，执行步骤或令牌开销应逐渐收敛。上述数值是官方命题目标，不代表本团队已经达到。

# Java 后端可靠性不是加个 `@Transactional`

很多项目把“可靠”理解成在 Service 方法上加一个 `@Transactional`。这只能解决一部分数据库原子性问题。一个真实请求往往还包括 Redis、消息队列、对象存储、短信、支付或第三方 API；数据库能够回滚，不代表这些外部副作用也会跟着回滚。

可靠性设计的核心问题不是“有没有注解”，而是：**失败发生在任意一步时，系统是否知道已经做了什么、能否安全重试、能否恢复到可解释的状态。**

**【配图位置 1：自制“HTTP 请求—应用服务—数据库—消息系统”边界图】**

## 先理解 Spring 事务实际在哪里生效

Spring 的声明式事务通常由代理拦截方法调用。外部调用进入代理后，代理创建或加入事务，再调用目标对象的方法。由此会产生一个经典陷阱：同一个对象内部使用 `this` 调用另一个带事务注解的方法，调用可能绕过代理，新的事务语义也就不会按预期生效。

```java
@Service
public class OrderService {

    public void importOrders(List<OrderCommand> commands) {
        for (OrderCommand command : commands) {
            this.createOrder(command); // 自调用可能绕过 Spring 事务代理
        }
    }

    @Transactional
    public void createOrder(OrderCommand command) {
        // 写入订单与库存流水
    }
}
```

更清晰的做法，是把需要独立事务语义的方法放到另一个 Spring Bean 中，或者重新设计批处理边界。不要为了“让注解生效”而隐藏调用关系；事务边界应当能从业务用例上被解释。

## 默认回滚规则经常与直觉不同

Spring 默认会对运行时异常和错误触发回滚，但受检异常默认不一定回滚。如果业务方法可能抛出受检异常，又要求数据库操作全部撤销，应显式定义回滚规则。

```java
@Transactional(rollbackFor = Exception.class)
public void confirmOrder(ConfirmCommand command) throws Exception {
    // 需要把失败语义设计清楚，而不是机械地捕获所有异常
}
```

另一个常见错误是捕获异常后只打印日志，不再抛出，也不显式标记事务回滚。对事务拦截器而言，方法正常返回就可能意味着可以提交。异常处理必须回答三个问题：这次操作是否成功、调用方应该看到什么、当前事务是否允许提交。

## 不要把慢速远程调用包进数据库事务

设想一个下单方法先锁定库存，再调用支付服务，最后更新订单。如果支付接口耗时 8 秒，数据库锁就可能被持有 8 秒以上。并发升高后，连接池和锁等待会把一个外部服务抖动放大成整个系统拥塞。

更稳妥的边界通常是：

1. 在短事务中校验并写入本地业务状态。
2. 同一个事务内写入待发送事件，也就是 Outbox 记录。
3. 事务提交后，由异步发布器把事件发送到消息系统。
4. 消费方以业务键保证幂等，重复消息不会产生重复结果。
5. 对持续失败的事件保留重试次数、最后错误和人工处理入口。

这不是免费获得“绝对一次”。它把跨系统一致性转换为可观察、可重试、可对账的最终一致性流程。

## 幂等要落到数据库约束

只在应用内先查询“是否处理过”，随后再插入，仍可能在并发下重复执行。应当让数据库唯一约束成为最后一道防线。

```sql
CREATE TABLE request_deduplication (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    idempotency_key VARCHAR(80) NOT NULL,
    result_reference VARCHAR(80) NOT NULL,
    created_at TIMESTAMP NOT NULL,
    UNIQUE KEY uk_idempotency_key (idempotency_key)
);
```

一个可用的幂等键还需要明确作用域和生命周期。例如“用户 ID + 接口 + 客户端请求号”通常比单独的随机字符串更容易审计。服务端应保存第一次成功结果，使相同请求再次到达时能返回一致响应，而不是简单报错。

## 可观测性不是多打几行日志

生产故障通常不是“代码在哪一行错了”这么简单，而是“哪个请求经过了哪些组件、在哪一步开始变慢、影响了多少用户”。日志、指标和链路追踪各自回答不同问题：

- 日志记录离散事件和业务上下文，例如订单号、错误类型和状态迁移。
- 指标描述整体趋势，例如请求量、失败率、延迟分位数、连接池等待和消息积压。
- 链路追踪连接一次请求跨越的服务与组件，帮助定位耗时和错误传播路径。

不要把密码、令牌、身份证号或完整请求体直接写入日志。业务标识也要按最小必要原则记录，并设置访问控制和保留周期。

**【配图位置 2：Spring 官方事务代理示意图或自制可观测性三角图】**

## 一份可执行的检查清单

1. 事务边界是否对应一个明确的本地业务不变量？
2. 是否存在同类内部调用导致事务代理被绕过？
3. 受检异常、运行时异常和主动捕获异常的行为是否经过测试？
4. 事务中是否包含不受控的网络调用或大文件操作？
5. 所有可能重试的写操作是否有数据库级幂等约束？
6. 状态变化是否有审计记录，失败任务是否能够重放或人工修复？
7. 日志、指标和追踪能否通过同一个请求标识关联？

事务、幂等和可观测性并不是三套独立能力。事务定义本地提交边界，幂等保证重试安全，可观测性让失败能够被发现和解释。三者结合，系统才真正具备恢复能力。

# 从互联网文本到会对话的模型

> 本文是对 Andrej Karpathy 公开视频课程《Deep Dive into LLMs like ChatGPT》的原创学习笔记，不是视频逐字稿。建议先建立整体地图，再带着问题观看原课程。

理解大语言模型最容易走进两个极端：一种把它看成“会思考的数据库”，另一种把它简化成“随机接龙”。Karpathy 的课程提供了更有用的工程视角：模型的底层目标确实是预测下一个 token，但我们看到的对话助手，是数据处理、预训练、后训练、评测和产品系统共同塑造的结果。

**【配图位置 1：课程视频标题页或公开视频画面，标注课程与作者】**

## 第一层：互联网文本如何变成训练数据

预训练并不是把网页原样交给模型。真实流程需要抓取、去重、质量过滤、安全过滤和数据混合。去重尤其重要：如果测试题或基准答案以近似形式出现在训练集中，模型看似很强，实际评测却失去了意义。

数据还会决定模型的默认倾向。高质量技术文档能帮助模型学习清晰结构，大量重复或低质量内容则可能放大噪声。因此，“模型架构一样”并不意味着“能力一样”；数据配方本身就是核心工程。

## 第二层：token 是模型真正看到的单位

模型不直接读取我们眼中的字符或单词。分词器把文本转换为 token 序列，再映射为整数。常见词片段可能只占一个 token，生僻字符串、代码、混合语言和特殊符号可能被拆成多个 token。

这会带来几个实际影响：

- 上下文窗口按 token 计量，不按汉字数或单词数计量。
- 代码中的一个微小字符差异可能对应完全不同的 token 序列。
- 拼写、倒序、精确计数等任务可能比语义问答更困难。
- 提示词成本和生成延迟都与 token 数量直接相关。

做 Agent 时，不应只统计“执行了几步”，还应记录每一步输入和输出的 token、工具调用耗时及失败原因。

## 第三层：预训练模型学习的是条件分布

Transformer 读取已有 token，通过注意力机制和前馈网络计算下一个 token 的概率分布。反复优化预测误差后，模型压缩了训练数据中大量关于语言、事实、代码和模式的统计结构。

但基础模型的直接目标不是“给用户一个诚实、有帮助的答案”。它更像一个能够续写各种互联网文本的生成器。要获得对话助手，还需要后训练把“下一段可能出现什么”转化为“面对用户请求应该怎样回应”。

## 第四层：后训练塑造助手行为

监督微调通过高质量示例告诉模型什么是合适的提问与回答格式。偏好学习或强化学习则进一步比较不同回答，使模型更倾向于有帮助、安全且符合任务要求的输出。

这里要区分两个概念：模型在预训练中获得广泛模式，后训练主要改变这些能力被调用和表达的方式。很多看似突然出现的“推理能力”，既与基础模型规模和数据有关，也与是否允许模型生成中间步骤、使用更长计算预算和接受针对性训练有关。

**【配图位置 2：自制“预训练 → 监督微调 → 偏好优化 → 产品助手”流程图】**

## 为什么模型会产生幻觉

如果问题要求一个具体答案，而上下文中没有可靠证据，模型仍然会按照学到的分布继续生成。流畅性来自预测能力，不等同于事实已经验证。要求模型“更自信”不会让缺失的信息自动出现。

工程上可以采用分层策略：

1. 对稳定常识允许模型直接回答。
2. 对时效信息使用检索，并保留来源和检索时间。
3. 对计算问题调用计算器、代码执行器或结构化工具。
4. 对高风险结论要求引用、交叉核验和人工确认。
5. 对无法验证的内容允许模型明确表达不确定性。

关键不是消灭所有错误，而是让系统知道哪些结论必须经过外部证据闭环。

## 从 LLM 到 Agent，多出来的是什么

一个 Agent 通常在模型之外增加状态、工具、记忆、循环控制和评测器。模型提出下一步动作，工具改变环境，系统读取新状态，再决定继续、重试或停止。真正困难的是控制环，而不是让模型输出一段看起来合理的计划。

可以用五个问题审查 Agent：

- 目标是否被转换为可验证的完成条件？
- 每个工具的输入、输出和失败语义是否明确？
- 系统如何知道当前观察是新的，而不是旧缓存？
- 历史轨迹进入记忆前，是否经过质量判断和隐私处理？
- 失败后是盲目重试，还是根据错误类型改变策略？

这也解释了为什么“从历史轨迹中学习”有价值：好的经验不是把整段对话无限塞回上下文，而是提炼对当前任务有用、可验证、能过期的策略。

## 一套更有效的学习方式

第一次观看时先画出端到端流程，只记录每一层解决什么问题。第二次选择自己最薄弱的环节，例如分词、注意力或强化学习，结合小实验验证。最后把认知落到一个可以测量的项目上：固定十个任务，记录成功率、步骤数、token 成本和错误类型，再改变一个变量做对照。

如果只能记住一句话，可以记住：**大模型给出的是基于上下文的候选分布，可靠产品还需要证据、工具、状态和评测。**

# 从数据结构课到 ICPC 赛场

数据结构课程通常按章节讲数组、链表、树、图和排序；竞赛题却不会告诉你“这是一道最短路”。它给出一个业务化场景、约束范围和输入输出，要求你识别模型、证明算法、控制复杂度并在一次提交中正确实现。

从课程到竞赛的差距，主要不在于多背几个模板，而在于建立一套稳定的问题求解流程。

**【配图位置 1：CSES Problem Set 分类页面】**

## 第一步永远是读约束

假设输入规模为 `n`：

- `n` 只有 20 左右时，可以考虑状态压缩或指数级搜索。
- `n` 在 1,000 左右时，平方复杂度有时可行，但要结合常数和时限。
- `n` 达到 100,000 或更高时，通常需要 `O(n log n)` 或 `O(n)`。

这些不是硬公式，而是排除错误方向的第一层过滤。还要同时观察值域、边数、查询次数、是否有负权、是否在线处理，以及结果是否可能超出 32 位整数。

读完题后，先写下三件事：输入规模允许什么复杂度、答案需要维护什么信息、算法为什么不会漏解或重复计算。

## 四层训练结构

### 第一层：实现与复杂度

目标是熟悉排序、二分、前缀和、双指针、递归、迭代和基本复杂度分析。每道题都应能解释时间复杂度和空间复杂度，而不是只说“运行通过”。

### 第二层：核心数据结构

掌握栈、队列、哈希表、堆、并查集、树状数组和线段树。学习重点不是记住代码长度，而是知道它维护的不变量。例如，并查集维护集合连通关系；堆只保证堆顶最优，不保证整体有序。

### 第三层：图论与动态规划

图论需要把 BFS、DFS、拓扑排序、最短路、最小生成树和强连通分量放进适用条件中比较。动态规划则要明确状态含义、转移来源、计算顺序和初始条件。状态定义如果不能用一句话解释，代码通常也会变得脆弱。

### 第四层：比赛策略

比赛训练要加入读题分工、题目优先级、提交检查和止损机制。ICPC 标准赛制是三人共用一台机器，沟通成本也是复杂度。队伍应在平时就约定变量含义、纸面推导格式和交叉检查方法。

## 一个通用解题闭环

1. 用自己的话重述输入、输出和目标。
2. 从样例中确认边界和容易误解的条件。
3. 根据约束列出可接受的复杂度。
4. 选择模型并写出正确性依据。
5. 在编码前准备最小、最大、重复、断开和溢出用例。
6. 提交后记录错误类别，赛后重新独立实现。

如果一道题看了解析后会做，但一周后仍不能独立完成，说明知识还没有进入可检索状态。复习时应隐藏代码，只保留题意、关键观察和失败原因。

## Java 参赛实现的稳定性细节

Java 完全可以用于 ICPC，但要主动控制输入输出和对象开销：

- 大输入使用 `BufferedInputStream` 自行解析，或使用经过验证的快速输入类。
- 批量输出写入 `StringBuilder`，最后统一打印。
- 距离、计数和乘法结果优先评估是否需要 `long`。
- 图的边数很大时，注意大量小对象带来的内存与垃圾回收成本。
- `PriorityQueue` 中可能保留旧距离，取出节点时要判断条目是否过期。

下面是 Dijkstra 的核心写法。它适用于边权非负的图。

```java
static long[] dijkstra(List<Edge>[] graph, int source) {
    long inf = Long.MAX_VALUE / 4;
    long[] dist = new long[graph.length];
    Arrays.fill(dist, inf);
    dist[source] = 0;

    PriorityQueue<State> queue =
            new PriorityQueue<>(Comparator.comparingLong(State::distance));
    queue.offer(new State(source, 0));

    while (!queue.isEmpty()) {
        State current = queue.poll();
        if (current.distance() != dist[current.vertex()]) {
            continue;
        }

        for (Edge edge : graph[current.vertex()]) {
            long candidate = current.distance() + edge.weight();
            if (candidate < dist[edge.to()]) {
                dist[edge.to()] = candidate;
                queue.offer(new State(edge.to(), candidate));
            }
        }
    }
    return dist;
}
```

这里最容易漏掉的是“过期条目判断”。Java 的优先队列不支持高效地原地降低键值，常见做法是把新距离再次加入队列，弹出时跳过与当前最短距离不一致的旧条目。

## 八周起步计划

1. 第 1 周：复杂度、排序、二分、前缀和，每天完成 2 至 3 道基础题。
2. 第 2 周：双指针、滑动窗口、栈、队列和哈希。
3. 第 3 周：DFS、BFS、连通性和拓扑排序。
4. 第 4 周：堆、并查集、最短路和最小生成树。
5. 第 5 周：一维与二维动态规划、背包和最长子序列。
6. 第 6 周：树、倍增、树状数组或线段树基础。
7. 第 7 周：混合专题训练，开始按五小时进行团队模拟赛。
8. 第 8 周：集中复盘错误题，整理个人模板并做第二次独立实现。

训练量不必机械追求。比“刷了多少题”更有价值的指标是：首次独立通过率、从读题到形成算法的时间、错误提交原因分布，以及一周后能否重新写出关键题。
